# 加班通報人與核准權限

**建立日期**：2026-11-06  
**狀態**：已實作，驗證與部署安排見 plan.md；尚未部署。  
**來源**：本次需求討論中使用者確認的加班申請規則。

## 背景與適用範圍

目前出勤申請的加班通報為選填，所有已登入者都能核准申請，包含申請人本人。本需求將加班通報改為必填，並收斂加班的核准權限。

本文件描述本次實作行為；正式環境需待前端及 Firestore Rules 部署後才生效。既有行為與權限依據見 [007 出勤更新與審核權限](../007-attendance-permission-hardening/spec.md) 與 [010 代理人代改](../010-attendance-proxy-editing/spec.md)。

僅調整加班申請的通報人填寫條件與核准資格；拒絕、退回待審及其他出勤類型的審核資格維持現狀。

## 名詞定義

| 名詞 | 定義 |
| --- | --- |
| 加班申請 | 類型為加班（Overtime）的出勤申請 |
| 申請人 | 申請單所屬人員，不一定是實際操作填單者 |
| 加班通報人 | 該筆申請指定的通報對象；本需求賦予其加班核准資格 |
| Admin | 系統既有管理員角色 |
| 系統中存在的使用者 | 在系統使用者資料中有對應紀錄的人員；不得僅以欄位非空或可在舊選單中找到判定 |
| 在職使用者 | 系統使用者資料中未填寫離職日（`exitDate` 無值）的人員；只要離職日有值即視為離職，不比較日期是否已到。離職日欄位存在但為空值者仍為在職 |

通報人不是代理人；被指定為通報人不會因此取得申請內容或附件編輯權。通報欄位也不代表本次要新增通知發送功能。

## 已確認需求

### 通報人填寫

- 加班申請的「加班通報」必填。
- 通報人必須是系統中存在的使用者。
- 通報人不得為該筆申請的申請人本人；代填情境仍以申請人判斷。
- 新增加班或改派通報人時，只能選擇在職使用者；任何離職日有值的使用者都不得被新指定，即使離職日在未來。
- 歷史申請已儲存的離職通報人予以保留，不自動清除或改派。
- 本次不增加部門或主管角色限制。

### 審核資格

| 操作 | Admin | 該筆申請的通報人（非 Admin） | 申請人（非 Admin） | 其他已登入者 | 未登入者 |
| --- | --- | --- | --- | --- | --- |
| 核准加班 | 允許 | 允許 | 不允許 | 不允許 | 不允許 |
| 拒絕加班 | 允許 | 允許 | 允許 | 允許 | 不允許 |
| 加班退回待審 | 允許 | 允許 | 允許 | 允許 | 不允許 |

- Admin 依角色具有核准資格，即使 Admin 同時是申請人；通報欄位仍不得指定申請人本人。
- 通報人與 Admin 以外的登入者，不得透過直接資料寫入繞過核准限制。
- 本矩陣定義操作者資格，不擴充現有畫面的狀態轉換入口。
- 其他出勤類型維持現行全員可審核規則。

### 歷史申請

- 上線前缺少通報人的歷史申請，上線後由人工處理。
- 不自動回填通報人，不以申請人或 Admin 自動代入。
- 已是 `pending` 的歷史申請可直接編輯補正，不需要再次執行退回待審。
- 已是 `approved` 或 `rejected` 的歷史申請不要求主動補正，維持原狀即可。
- 缺少通報人的歷史申請仍可被拒絕或退回待審，不得因通報人必填而阻擋這兩項操作。
- 歷史申請一旦處於 `pending`，再次核准前必須先補正合法通報人；Admin 也不得略過補正直接核准。
- 編輯歷史申請的內容時，必須補填合法通報人。純附件異動維持既有附件管理規則，不視為內容編輯。
- 人工處理的責任人、執行批次及完成期限由上線安排另行決定。

### 通報人與使用者狀態

- 使用者不會由系統刪除；離職者仍保留使用者資料，因此仍符合「系統中存在的使用者」，但不得被新指定或改派為通報人。
- 只要使用者資料的離職日有值即視為離職，不論離職日是否已到；離職日為空值者仍為在職。
- 若已指定的通報人後來離職，僅 Admin 可核准該筆加班；任何已登入者仍可依既有規則拒絕或退回待審。

### 狀態與類型轉換

- 核准操作必須從 `pending`（待審）狀態進行；不開放從 `rejected` 直接轉為 `approved`。
- 上述 `pending → approved` 限制及加班核准資格只套用加班申請；其他出勤類型維持現行 Firestore Rules。
- 任何轉入 `approved` 的加班路徑都必須套用加班核准資格。
- 申請類型只能在待審時由既有內容編輯流程調整；核准 UI 不提供同時修改內容的介面。
- 所有人包含 Admin 都不得在同一筆寫入中修改申請內容並核准。內容必須先在待審狀態另行儲存，核准再以只變更狀態的另一筆操作完成。
- 從其他類型改為加班時，必須立即符合通報人必填、存在且不得為申請人的條件；後續核准套用加班資格。
- 從加班改為其他類型後，後續核准維持其他出勤類型的既有規則。
- 通報人被改派後，下一次核准以最新儲存的通報人判定，原通報人立即失去核准資格。改派不會讓新通報人取得內容或附件編輯權。

## 實作時需涵蓋的驗證情境

以下為落實已確認規則所需的驗證範圍，不表示已完成實作或測試。

| 情境 | 預期結果 |
| --- | --- |
| 新增加班，通報人為空 | 阻擋儲存並說明必填 |
| 通報人不存在 | 阻擋儲存並要求選擇有效使用者 |
| 通報人等於申請人 | 阻擋儲存並說明不可指定本人 |
| 新增或改派時選擇已有離職日的使用者 | 阻擋儲存；即使離職日在未來亦相同 |
| 代填者與申請人不同 | 以申請人作為不得相同的比較對象 |
| 編輯通報人、變更申請人或將其他類型改為加班 | 重新驗證通報人必填、存在且不同於申請人 |
| 非 Admin 的合法通報人核准 | 允許 |
| Admin 核准合法加班 | 允許；若申請正在待審且缺少通報人，仍須先另行補正 |
| 非 Admin 申請人或無關登入者核准 | 畫面不提供可執行入口，直接資料寫入也須拒絕 |
| 任一已登入者拒絕或退回待審 | 保留操作資格，包含申請人 |
| 缺少通報人的歷史申請被拒絕或退回待審 | 允許，不受通報人必填限制阻擋 |
| 已在待審且缺少通報人的歷史申請被核准 | 拒絕；先編輯補正後才能核准，不需再次退回待審 |
| 已核准或已拒絕且缺少通報人的歷史申請 | 維持原狀，不要求主動補正；若退回待審並要再次核准，須先補正 |
| 編輯缺少通報人的歷史申請內容 | 必須同時補填合法通報人 |
| 歷史申請缺少後續新增的欄位，僅異動附件 | 不視為內容編輯，不要求補正通報人 |
| 在職者的離職日欄位存在但為空值 | 視為在職，可被指定為通報人並核准 |
| 通報人離職後核准 | 僅 Admin 可核准；任何已登入者仍可拒絕或退回待審 |
| 通報人改派後由原通報人核准 | 拒絕；以最新儲存的通報人為準 |
| Admin 同時補填通報人並核准 | 拒絕；先在待審狀態儲存內容，再以另一筆狀態操作核准 |
| 從其他類型改為加班 | 僅於待審內容編輯流程進行，立即驗證通報人，後續核准套用加班資格 |
| 從加班改為其他類型 | 僅於待審內容編輯流程進行，後續核准適用該類型既有規則 |
| 從拒絕直接轉為核准 | 拒絕；必須先退回待審 |
| 非加班申請由一般登入者審核 | 維持原行為 |
| 以舊畫面或直接資料介面送出不合法的通報人 | 不得只依賴前端驗證，資料存取層亦須拒絕 |

## 已確認邊界

下列邊界已納入本次需求，實作與測試均須遵守。

| 邊界 | 定案規則 |
| --- | --- |
| 歷史申請缺通報人的狀態操作 | 已核准／已拒絕資料不主動補正；允許拒絕或退回待審。處於待審時須先補正才能核准，原本已待審者可直接編輯補正 |
| 歷史內容與附件更新 | 編輯內容時要求補填合法通報人；純附件異動維持既有附件規則 |
| Admin 的填寫驗證 | Admin 同樣遵守通報人必填、存在且不得為申請人的條件；新增或改派須在職，既有離職通報值可保留 |
| 核准同時變更內容 | 禁止所有人包含 Admin 混合更新；類型與通報人須先在待審內容編輯流程儲存，再以另一筆只變更狀態的操作核准 |
| 通報人被改派 | 下一次核准以最新儲存的通報人判定，舊通報人立即失去核准資格 |
| 通報人選擇與事後離職 | 只要離職日有值就不得新指定或改派；歷史值保留。通報人離職後僅 Admin 可核准，任何已登入者仍可拒絕或退回待審 |
| 申請類型變更 | 只在待審內容編輯流程進行；其他類型改成加班後套用加班限制，加班改成其他類型後套用該類型既有規則 |
| 狀態轉換範圍 | 加班核准必須從待審進入，且任何轉入核准的加班路徑均須驗證通報人或 Admin 資格；其他類型維持現行 Rules |

## 不在本次需求範圍

- 改變既有內容編輯、代理人代改、附件管理與代申請政策。
- 新增獨立主管角色、分層簽核、通知寄送或通報人接受指派流程。
- 補齊所有出勤欄位的資料庫驗證，例如時數必填、半小時倍數、日期先後或時數與區間一致性。
- 自動修改歷史資料、執行正式環境資料清理或部署。
