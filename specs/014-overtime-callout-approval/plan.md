# 加班通報與核准實作

## 實作對應

- `attendance-permission.ts` 共用核准資格與離職判定。`exitDate` 有值（前端 truthy、Rules 非 `null`／`''`）即視為離職，不比較日期。使用者進階設定存檔會寫入 `exitDate: ''` 或 `null`，因此不可以欄位存在判斷。
- 申請表單驗證通報必填、存在且不得為申請人。新增與改派排除離職者，原有離職值可顯示並保留。
- 更新 patch 由 `diffAttendance` 計算：舊文件缺少的欄位若表單為空值（`''`／`null`）則不列入異動，避免純附件更新夾帶空欄位而被 Rules 判定為內容編輯。
- 表單以載入時的內容快照辨識純附件異動，缺通報人的歷史資料不因純附件變更而被要求補正；內容變動即重新驗證。
- 清單依目前使用者及通報人資料顯示核准入口。
- 審核交易重新讀取申請，拒絕以過期狀態、類型或通報人審核。加班核准另讀操作者及通報人資料；資料庫規則為最終權限邊界。

## Firestore 邊界

- 新增加班必須為 pending 且指定合法在職通報人，避免直接建立已核准資料。
- 加班建立與更新驗證放在 Admin／本人／代理人授權分支外，Admin 也不得略過。
- 涉及加班的狀態變更只能修改 status；核准必須從 pending 進入，且既有通報人有效。通報人已離職時僅 Admin 可核准。
- 以更新前後類型共同判斷是否涉及加班，防止同時改類型與核准繞過限制；類型調整須在 pending。
- 不變更狀態、且只影響 attachments／updatedAt 的更新不觸發通報人補正；其他內容更新需通報人有效。保留原通報人時可為離職者，新指定則必須在職。
- 非加班的既有審核與附件權限保持原樣，所有更新仍須通過既有授權及附件數量限制。

## 驗證

- 前端測試：出勤元件與共用權限測試，包含新建驗證、申請人變更、歷史純附件、未來離職日、空值離職日視為在職、缺欄位 diff 及 Admin 資格。
- Rules 測試：`tools/attendance-permission-emulator-tests.cjs` 擴充直接寫入矩陣，涵蓋自我核准、改派、混合更新、歷史補正、離職（含 `exitDate` 為 `''`／`null` 的在職者）與類型轉換，以及非加班回歸。
- TypeScript 編譯及差異格式檢查。

## 部署與人工處理

先部署較嚴格的 Firestore Rules，再部署前端。短暫期間舊前端可能顯示無權核准入口或送出不合法通報資料；規則會拒絕，更新前端後恢復正確提示。正式部署另行執行。

不自動回填。歷史 approved／rejected 維持原狀；pending 缺通報人於內容編輯或下次核准前人工補正。人員安排與時程由上線作業決定。
